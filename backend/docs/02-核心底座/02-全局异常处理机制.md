# 02-全局异常处理机制

## 1. 功能概述

在 Spring Boot 应用中，如果 Controller 抛出未捕获的异常，Tomcat 会返回一个 HTML 格式的错误页面（Whitelabel Error Page）。这对前后端分离的 API 服务来说是灾难性的——前端期望 JSON 响应，收到的却是 HTML。

`GlobalExceptionHandler` 利用 Spring 的 `@RestControllerAdvice` 机制，全局拦截所有异常，统一转换为标准的 `Result` JSON 格式返回。

**对比**：

```text
# 没有全局异常处理（Controller 抛出 RuntimeException）
HTTP 500 -> <html><body>Whitelabel Error Page...</body></html>
前端接收 HTML，无法解析，用户体验极差

# 有全局异常处理（BareZen_Base 做法）
HTTP 200 -> {"code":500,"msg":"具体的错误信息","data":null}
前端接收标准 JSON，自动弹出错误提示
```

---

## 2. 设计原理

### 2.1 @RestControllerAdvice 机制

`@RestControllerAdvice` 是 Spring 3.2 引入的注解，它是 `@ControllerAdvice` + `@ResponseBody` 的组合：

- `@ControllerAdvice`：声明此类为全局控制器增强，可以拦截所有 Controller 的方法。
- `@ResponseBody`：返回值自动序列化为 JSON（而非视图名）。

Spring 在调用 Controller 方法前后会执行 Advice 链。如果方法抛出异常，Spring 会查找匹配的 `@ExceptionHandler` 方法处理。

### 2.2 异常处理的优先级

```text
Controller 抛出异常
  -> 查找最匹配的 @ExceptionHandler 方法
     -> 存在 RuntimeHandler？ -> 处理 RuntimeException
     -> 存在 ExceptionHandler？ -> 处理其他所有异常
     -> 都不匹配？ -> 继续抛出，Tomcat 返回 500 页面
```

Spring 会优先选择最具体的异常处理器：
1. 先匹配异常类型（RuntimeException 优先于 Exception）
2. 同类型时按方法声明顺序

### 2.3 日志级别区分

不同类型的异常使用不同的日志级别：

- **RuntimeException**（业务异常）：`warn` 级别。业务异常是预期内的，如"用户名已存在"、"余额不足"。使用 warn 避免日志告警泛滥。
- **Exception**（系统异常）：`error` 级别。系统异常是非预期的，如 NullPointerException、数据库连接失败。使用 error 触发运维告警。

## 4. 代码实现

文件路径：`bz_framework_core/src/main/java/com/linan/core/common/exception/GlobalExceptionHandler.java`

```java
package com.linan.core.common.exception;

// 引入统一返回体，异常处理的结果必须使用标准格式
import com.linan.core.common.api.Result;
// Lombok 的日志注解：自动生成 private static final Logger log = ...
import lombok.extern.slf4j.Slf4j;
// Spring 的异常处理器注解：标记此方法处理某种异常
import org.springframework.web.bind.annotation.ExceptionHandler;
// Spring 的全局控制器增强注解：拦截所有 @Controller 和 @RestController
import org.springframework.web.bind.annotation.RestControllerAdvice;

/**
 * 全局异常处理器
 *
 * 拦截所有 Controller 抛出的未捕获异常，统一转换为 Result JSON 格式返回。
 * 确保后端永远不会直接向前端暴露 Tomcat 的默认错误页面。
 *
 * 处理策略：
 * 1. RuntimeException（业务异常）-> 记录 warn 日志，返回用户友好的错误信息
 * 2. Exception（系统异常）-> 记录 error 日志，返回通用错误提示，不暴露内部细节
 */
@Slf4j                          // Lombok：自动生成 log 对象（SLF4J 日志门面）
@RestControllerAdvice           // Controller 增强 + JSON 响应
public class GlobalExceptionHandler {

    /**
     * 处理所有未捕获的通用异常（兜底处理器）
     *
     * 当抛出的异常不是 RuntimeException 时（如 IOException、SQLException），
     * 由此方法兜底处理。
     *
     * 返回通用错误信息而不暴露堆栈信息给前端，是安全最佳实践——
     * 防止敏感信息（数据库表名、SQL 语句、服务器路径）泄露。
     *
     * @param e 捕获的异常对象
     * @return Result 对象，code=500，msg 为通用提示
     */
    @ExceptionHandler(Exception.class)          // 声明此方法处理 Exception 及其子类
    public Result<?> handleException(Exception e) {
        // 记录完整堆栈日志，方便运维人员排查问题
        // 第一个参数是日志消息模板，第二个参数是异常对象（SLF4J 会自动追加堆栈）
        log.error("系统未知异常: ", e);

        // 向前端返回通用错误提示，不暴露异常细节
        return Result.error("服务器开小差了，请稍后再试");
    }

    /**
     * 处理运行时异常（业务异常）
     *
     * 在业务逻辑中，当遇到预期内的错误（如数据校验不通过、资源不存在），
     * 应抛出 RuntimeException 并携带用户可读的错误信息。
     *
     * 例如：
     * throw new RuntimeException("用户名已存在");
     * throw new RuntimeException("订单状态不允许删除");
     *
     * 此方法提取异常信息，以 warn 级别记录日志（不需要运维告警），
     * 并将错误信息原样返回给前端。
     *
     * @param e 捕获的 RuntimeException 对象
     * @return Result 对象，code=500，msg 为异常携带的错误信息
     */
    @ExceptionHandler(RuntimeException.class)   // 声明此方法处理 RuntimeException
    public Result<?> handleRuntimeException(RuntimeException e) {
        // 使用 warn 日志级别而非 error
        // 因为业务异常是预期内的，不需要触发运维告警
        // {} 是 SLF4J 的占位符，运行时会被 e.getMessage() 替换
        log.warn("业务异常: {}", e.getMessage());

        // 将异常信息原样返回给前端
        // 要求业务代码在抛出 RuntimeException 时携带清晰的中文提示
        return Result.error(e.getMessage());
    }

    /*
     * ==================== 扩展点 ====================
     *
     * 以下方法可根据项目需要添加，目前注释掉以保持简洁。
     * 需要时取消注释并实现即可。
     */

    /*
     * 示例：参数校验异常处理
     *
     * 当使用 @Validated/@Valid 注解校验参数失败时，
     * Spring 会抛出 MethodArgumentNotValidException。
     * 此方法提取第一个校验错误信息返回给前端。
     *
     * @ExceptionHandler(MethodArgumentNotValidException.class)
     * public Result<?> handleValidationException(MethodArgumentNotValidException e) {
     *     String errorMsg = e.getBindingResult()
     *         .getFieldErrors()
     *         .stream()
     *         .map(f -> f.getField() + ": " + f.getDefaultMessage())
     *         .collect(Collectors.joining(", "));
     *     log.warn("参数校验失败: {}", errorMsg);
     *     return Result.error(errorMsg);
     * }
     */

    /*
     * 示例：自定义业务异常处理
     *
     * 如果项目存在自定义异常类（如 BizException extends RuntimeException），
     * 可以单独处理以返回特定的状态码。
     *
     * @ExceptionHandler(BizException.class)
     * public Result<?> handleBizException(BizException e) {
     *     log.warn("业务异常: code={}, msg={}", e.getCode(), e.getMessage());
     *     return new Result<>(e.getCode(), e.getMessage(), null);
     * }
     */

    /*
     * 示例：404 资源不存在处理
     *
     * 当请求的 URL 不匹配任何 Controller 时，
     * Spring Boot 默认返回 404 页面。可配置以下实现返回 JSON。
     * （需要在 application.yml 中设置 spring.mvc.throw-exception-if-no-handler-found=true）
     *
     * @ExceptionHandler(NoHandlerFoundException.class)
     * public Result<?> handle404(NoHandlerFoundException e) {
     *     log.warn("请求路径不存在: {}", e.getRequestURL());
     *     return Result.error("请求路径不存在");
     * }
     */
}
```

## 5. 使用说明

### 5.1 在业务代码中抛出异常

```java
@Service
public class UserService {

    public User getById(Long id) {
        User user = userMapper.selectById(id);
        if (user == null) {
            // 抛出 RuntimeException，GlobalExceptionHandler 会自动处理
            // 前端收到：{"code":500,"msg":"用户不存在","data":null}
            throw new RuntimeException("用户不存在");
        }
        return user;
    }

    public void createUser(User user) {
        if (userMapper.existsByUserName(user.getUserName())) {
            throw new RuntimeException("用户名已存在");
        }
        userMapper.insert(user);
    }
}
```

### 5.2 自定义业务异常类（可选扩展）

当前项目直接使用 `RuntimeException` 携带错误信息。如果需要在异常中携带状态码等更多信息，可以创建自定义异常类：

```java
package com.linan.core.common.exception;

import lombok.Getter;

/**
 * 业务异常类
 * 用于在业务逻辑中抛出带有自定义状态码的异常
 */
@Getter
public class BizException extends RuntimeException {

    /** 错误状态码 */
    private final int code;

    /**
     * 使用默认状态码 500 创建业务异常
     * @param msg 错误信息
     */
    public BizException(String msg) {
        super(msg);
        this.code = 500;
    }

    /**
     * 使用自定义状态码创建业务异常
     * @param code 错误状态码
     * @param msg  错误信息
     */
    public BizException(int code, String msg) {
        super(msg);
        this.code = code;
    }
}
```

然后在 `GlobalExceptionHandler` 中添加对应的处理：

```java
@ExceptionHandler(BizException.class)
public Result<?> handleBizException(BizException e) {
    log.warn("业务异常: code={}, msg={}", e.getCode(), e.getMessage());
    return new Result<>(e.getCode(), e.getMessage(), null);
}
```

## 6. 异常处理流程示意

```text
Controller: userService.deleteUser(999)
   |
   v
Service: userMapper.selectById(999) -> null
   |
   v
Service: throw new RuntimeException("用户不存在")
   |
   v
Spring 拦截异常，查找 @ExceptionHandler
   |
   v
匹配到 handleRuntimeException(RuntimeException e)
   |
   v
log.warn("业务异常: 用户不存在")
   |
   v
return Result.error("用户不存在")
   |
   v
Jackson 序列化为 JSON -> {"code":500,"msg":"用户不存在","data":null}
   |
   v
HTTP Response 返回给前端
```

## 7. 安全注意事项

**不要将异常堆栈返回给前端**：

```java
// 错误做法：暴露内部信息
@ExceptionHandler(Exception.class)
public Result<?> handleException(Exception e) {
    return Result.error(e.toString());  // 可能包含 SQL 语句、包路径等敏感信息
}

// 正确做法：返回通用提示，堆栈仅写入日志
@ExceptionHandler(Exception.class)
public Result<?> handleException(Exception e) {
    log.error("系统未知异常: ", e);       // 完整堆栈写入日志
    return Result.error("服务器开小差了，请稍后再试");  // 通用提示返回前端
}
```

## 9. 常见问题

**Q: 为什么返回 HTTP 200 而不是 500？**

A: 本框架采用"HTTP 层面统一 200，业务状态由 code 字段区分"的策略。这样做的好处是前端不需要处理 HTTP 层面的错误状态码，统一通过 `code` 字段判断即可。如果团队习惯 HTTP 语义，可以在 `@ExceptionHandler` 方法上添加 `@ResponseStatus(HttpStatus.INTERNAL_SERVER_ERROR)` 注解。

**Q: @ExceptionHandler 的优先级是怎样的？**

A: Spring 选择匹配度最高的处理器。如果有两个 `@ExceptionHandler` 分别处理 `RuntimeException` 和 `Exception`，抛出的异常是 `RuntimeException`，则匹配到前者。抛出的异常是 `IOException`（非 RuntimeException），则匹配到后者。

**Q: 如何在开发环境看到完整异常信息？**

A: 日志配置中设置 `logging.level.root=DEBUG` 可以看到更详细的日志。IDEA 控制台中也会打印完整堆栈。
