# 03-角色管理模块

## 1. 功能概述

角色管理模块实现系统角色的增删改查功能。角色是 RBAC 权限模型中的核心概念，它充当了用户与权限之间的桥梁。

**为什么需要角色？**

假如系统中有 100 个用户，每个用户都需要分配"用户管理"的权限。如果没有角色：
1. 你需要分别给 100 个用户依次设置权限
2. 如果"用户管理"的权限标识变化了，你需要更新 100 个用户的权限
3. 新增功能时，你仍然需要更新 100 个用户的权限

有了角色后：
1. 创建一个"管理员"角色，分配"用户管理"权限
2. 将这 100 个用户都赋予"管理员"角色
3. 权限变化时，只需修改角色的权限，100 个用户自动生效

**角色相关表关系**：
```
sys_user (1) ----< sys_user_role >---- (M) sys_role (M) ----< sys_role_menu >---- (M) sys_menu
```

角色与用户是多对多关系（一个角色可以有多个用户，一个用户可以有多个角色），通过 sys_user_role 关联表实现。

## 2. 设计原理

### 2.1 角色标识（role_key）

角色标识 `role_key` 是角色的唯一标识，在代码中用于判断角色类型。命名规则：

| role_key | 角色名称 | 说明 |
| :--- | :--- | :--- |
| admin | 超级管理员 | 拥有系统所有权限，不受权限约束 |
| common | 普通角色 | 仅拥有被分配的权限 |
| custom_xxx | 自定义角色 | 可根据业务灵活创建 |

`admin` 是系统内置角色，具有最高权限。在 AuthInterceptor 或 AOP 切面中可检查是否 admin 角色，如果是则直接放行，无需校验权限。

### 2.2 状态管理（status）

角色的 `status` 字段为 `0` 时表示停用。停用的角色下所有用户立即失去该角色拥有的所有权限。这种设计常用于：
- 临时禁止某个角色的访问权限（如系统维护期间）
- 发现角色分配了不恰当的权限时紧急停用

### 5.2 新增角色

```
请求方式：POST
请求URL：/api/system/v1/roles
请求体：
{
  "roleName": "数据管理员",
  "roleKey": "data_admin",
  "roleSort": 3,
  "status": "1",
  "remark": "负责数据管理"
}
```

### 5.3 删除角色

```
请求方式：DELETE
请求URL：/api/system/v1/roles/2
```

**注意**：删除角色时，数据库中的关联数据（sys_user_role、sys_role_menu）不会被自动删除。如果希望删除角色时联动清理关联数据，需要在 Service 中手动实现。

### 5.4 给角色分配菜单权限

```
请求方式：PUT
请求URL：/api/system/v1/roles/1/menus
请求体：[1, 2, 5, 8] （菜单ID数组）
```

该接口会先清空角色原有的菜单关联，再批量插入新的关联关系。

## 7. 常见问题

**Q: 为什么继承 BaseController 后接口路径是 /list 而不是 /page？**

A: 这是 BaseController 中定义的默认路径名。前端 Element Plus 的分页组件通常使用 list 表示获取分页数据的接口。如果业务需要，可以在子 Controller 中覆盖 `list` 方法。例如：
```java
@Override
@GetMapping("/page")
public Result<IPage<SysRole>> list(...) {
    return super.list(pageNum, pageSize);
}
```

**Q: 怎么实现"一个用户有多个角色"？**

A: 不需要在代码层面做特殊处理。MyBatis-Plus 的通用 CRUD 不涉及关联查询。当需要查询用户的角色列表时，自定义 Mapper 方法写 LEFT JOIN 查询即可：
```sql
SELECT r.* FROM sys_role r
LEFT JOIN sys_user_role ur ON r.id = ur.role_id
WHERE ur.user_id = #{userId} AND r.del_flag = 0
```
